### 터미널 데이터 처리 판단

처음 만든 터미널 JSONL은 `max_instruction_chars=24000`, `max_response_chars=12000`으로 51.76GB였고 2,140,488 examples를 만들었다. 그러나 `context-size=4097`에서 대부분 instruction 중간부가 잘려 토큰화 I/O가 낭비되는 것이 확인됐다.

따라서 모든 parquet row와 assistant response 내용을 계속 쓰되, 최종 학습 context에 더 맞도록 `max_instruction_chars=9000`, `max_response_chars=6000`으로 다시 변환했다. 이 버전은 response가 길면 더 작은 chunk로 나누므로 example 수는 2,739,207개로 늘었고, 원문 JSONL은 33.95GB로 줄었다.

토큰 전처리는 단일 프로세스가 너무 느려 8개 shard로 분할한 뒤 병렬로 처리하고 merge했다.

- merged output: `/home/work/.data/hrm_text_prepared/local_terminal_conversations_ctx9k_resp6k_v1`
- samples: 2,739,207
- tokens: 9,386,532,467
- avg sample length: 3,426.7
- max sample length: 4,096
- disk usage: 약 36GB
- 중간 산출물 정리 후 `.data` 여유 공간: 약 1007GB

## 전처리 진행

SWE-ZERO 샘플 길이 점검:

- 첫 2,000개 샘플 기준 평균 약 3,686 tokens, p95 약 7,081 tokens, max 약 11,011 tokens.
- HRM paper 기본과 맞춘 `context-size=4097`에서는 긴 trajectory가 그대로는 실패한다.
- 해결 방식: response는 보존하고 instruction은 앞부분 시스템 지시 일부와 최근 맥락을 남기는 `truncate-instruction-middle` 사용.
- 현재 목적이 terminal/code action 학습이므로, 긴 샘플을 대량 drop하는 것보다 최근 터미널 맥락을 보존하는 절단이 더 낫다.

| 262,144 | 32,768 | XL / KoHRM-Text-1.4B 360/2713 step에서 OOM. bp warmup으로 backward depth가 증가한 뒤 final logits buffer `32,768 x 131,072` bf16 8GB 추가 할당에 실패 |
| 196,608 | 24,576 | XL / KoHRM-Text-1.4B 재시작. 논문 global batch와 동일한 안정 설정 |

비교:

- HRM-Text 논문은 bfloat16, context 4096, vocab 65,536, global batch 196,608 tokens를 사용했다.
- 논문 1B run은 16 x H100 기준이라 GPU당 local batch는 12,288 tokens다.
- 262,144 run은 8 x H200에서 GPU당 local batch 32,768 tokens라 논문 GPU당 local batch의 약 2.67배였지만, 131,072 vocab의 logits 메모리와 HRM bp warmup 증가가 겹쳐 실패했다.
- 196,608 run은 논문 global batch와 같고, 8 x H200에서 GPU당 local batch 24,576 tokens다. 여전히 논문 16 x H100의 GPU당 12,288 tokens 대비 2배다.

전체 학습 규모 기준:

- HRM-Text 논문/기존 cleaned 데이터 축은 약 40B unique tokens로 본다.
- 우리가 추가하려는 SWE-ZERO, GLM reasoning, 한국 법령/조례/행정규칙/판례, ToolBench, local terminal/code 데이터를 모두 task화해서 포함하면 추가 약 10~12B tokens로 추정한다.
- 따라서 KoHRM-Text full pretraining 목표 규모는 보수적으로 45~48B, 기본 계획으로 50~52B, 공격적으로 structured wiki와 더 많은 SWE/GLM을 포함하면 55B+까지 가능하다.

### Colab probe correction after SFT-free checkpoint outputs

사용자가 Colab에서 확인한 출력은 strict assistant benchmark 관점에서는 나빴다.

```text
legal JSON -> 엉뚱한 schema 또는 markdown-wrapped JSON
wiki summary -> placeholder/garbage token
finance QA -> 반복 또는 HTML-like fragment
terminal command -> command가 아니라 설명/의도 문장
python code -> syntax/logic가 맞지 않는 함수
```

원인 판단:

```text
1. 현재 공개 weight는 final SFT/chat checkpoint가 아니라 rolling pretraining checkpoint다.
2. KoHRM pretraining은 instruction-response response-only loss라 SFT와 수식은 비슷하지만, 행동 정렬 단계는 아직 끝나지 않았다.
3. JSON-only, command-only, code-only는 pretraining 신호만으로 안정화되기 어렵고, behavior_mini / terminal_tool_core / korean_domain_core LoRA 또는 SFT가 필요하다.
4. prompt를 과도하게 복잡하게 만드는 것은 해결책이 아니다. 학습 데이터는 <boq><condition><instruction><eoq><response><eoa>의 깔끔한 구조이고, smoke test도 이 구조와 direct condition을 유지해야 한다.
```

수정 사항:

- `notebooks/kohrm_colab_generate.py`
  - upstream `InferenceCheckpoint.tokenize_prompt(condition, prompt)`와 맞춰 `condition_to_tokens()`와 `condition="direct"` API를 추가했다.
  - 기존 `condition_token` override는 backward compatibility로 남겼다.
  - prompt wrapper는 `<|im_start|><condition_tokens>prompt<|im_end|>`를 유지하고 `<|box_end|>`에서 stop한다.

- `notebooks/KoHRM_Text_1_4B_Colab_T4_Smoke_Test.ipynb`
  - 이름과 설명을 `Pretraining Checkpoint Probe`로 바꿨다.
  - pretraining-distribution probe와 strict post-training probe를 분리했다.
  - validator는 JSON parse, one-line shell command, Python AST, Korean placeholder artifact를 엄격하게 본다.
  - strict failure는 최종 품질 실패가 아니라 post-training readiness signal로 출력되게 했다.

- 문서/모델 카드
  - Colab 복붙 코드를 `condition="direct"` 기준으로 업데이트했다.
  - SFT 전 checkpoint의 나쁜 출력 해석 기준과 future auto-guidance 실험 가능성을 `POST_TRAINING_HRM_TEXT_GUIDE_2026-05-30.md`에 추가했다.

### Long PT knowledge notebook correction

사용자 Colab 재실행 결과를 보면 strict probe 설계 자체가 pretraining checkpoint 확인 목적과 맞지 않았다. JSON-only, command-only, code-only, 짧은 grounded summary는 SFT/LoRA/RL 이후 behavior alignment를 볼 때는 필요하지만, 아직 PT 중인 checkpoint의 지식 신호를 보는 용도로는 과도했다.

수정 판단:

```text
1. 현재 모델은 SFT/chat checkpoint가 아니라 pretraining-stage rolling checkpoint다.
2. 학습 데이터는 <boq><condition><instruction><eoq><response><eoa> 구조의 response-only loss이며, artificial benchmark wrapper가 아니다.
3. PT 확인에서는 strict validator보다 긴 생성에서 도메인 용어, 문체, 반복 억제, 깨진 artifact를 직접 봐야 한다.
4. strict JSON/command/code는 별도 LoRA/SFT/RL 단계에서 측정한다.
```

수정 사항:

- `notebooks/KoHRM_Text_1_4B_Colab_T4_Long_Knowledge_Probe.ipynb`를 새로 추가했다.
- 기존 `KoHRM_Text_1_4B_Colab_T4_Smoke_Test.ipynb`는 링크 호환을 위해 남기되, 내용은 long knowledge probe와 동일하게 바꿨다.
- `notebooks/kohrm_colab_generate.py`에 `min_new_tokens`를 추가해 너무 짧게 `Yes`, `B`, 숫자 하나로 끝나는 출력을 막고 긴 생성 확인을 가능하게 했다.
- prompt는 BCAI 금융 QA, `build_kowiki_raw_hrm_jsonl.py`, `build_legal_raw_hrm_jsonl.py`, terminal/coding conversation builder 스타일과 맞췄다.
- README, docs README, model card, post-training guide에서 strict smoke benchmark 설명을 제거하고 long PT knowledge probe로 바꿨다.

남은 해석 기준:

```text
긴 생성도 계속 placeholder, HTML fragment, 무의미한 single-token answer로 무너지면
1. checkpoint 자체가 아직 덜 학습된 것인지,
2. public safetensors 변환 또는 Colab lightweight runtime이 raw training runtime과 어긋난 것인지,
3. decoding 설정이 해당 checkpoint에 맞지 않는지
를 raw checkpoint inference와 대조해야 한다.
```
